# CRD-based alerting (project-eks-crd)

This variant keeps **everything about metric collection the same** as `project-eks` — metrics are
still **OTel-only** (hostmetrics + kubeletstats + k8s_cluster on both clusters, Prometheus as a
remote-write TSDB). The one difference is **how alerting is defined and delivered**: declaratively,
through **Prometheus Operator CRDs**, with e-mail sent via **Amazon SES**.

---

## The model: who owns what

Each **service owns its alerting end to end** — both *what* to alert on **and** *who is paged* — in its
own chart. The only thing shared across the fleet is the **SES transport** (the SMTP server), configured
once.

```
   ┌──────────────────────── per SERVICE (app/<svc> chart) ───────────────────────┐
   │  templates/prometheusrule.yaml     ──helm──▶ PrometheusRule <svc>-alerts       │
   │    = WHAT to alert on (RED + pod/deploy health, scoped to this service)        │
   │  templates/alertmanagerconfig.yaml ──helm──▶ AlertmanagerConfig <svc>-routing  │
   │    = WHO is paged (this service's own emails / criticalEmails)                 │
   └───────────────────────────────────────────┬──────────────────────────────────┘
                                                │  operator selects (label
                                                │  alertmanagerConfig=app-monitoring)
                                                │  + merges all of them
   ┌──────────────────────── central transport (kube-prometheus-stack) ───────────┐
   │  Alertmanager base config = HOW e-mail is sent — Amazon SES smarthost/auth/TLS │
   └───────────────────────────────────────────────────────────────────────────────┘
```

| Concern | Lives in | Kind |
|---|---|---|
| **What to alert on** (per service) | `app/<svc>/templates/prometheusrule.yaml` (from its `values.yaml` `monitoring:` block) | `PrometheusRule` |
| **Who is paged** (per service's own recipients) | `app/<svc>/templates/alertmanagerconfig.yaml` (from the same `monitoring:` block) | `AlertmanagerConfig` |
| **How e-mail is sent** (SES host, auth, TLS, From) | `values/kube-prometheus-stack.yaml` | Alertmanager global config |

**Why this split:** a service's alerting ships *with that service* — change a threshold, or who gets the
e-mail, by editing that one chart and nothing else. The operator merges every service's
`AlertmanagerConfig` into Alertmanager automatically, so adding or re-homing a service needs no central
edit. Only the SES transport (one SMTP server for everyone) is configured once, centrally.

## Per-service rules (what to alert on)

Every `app/<svc>` chart carries `templates/prometheusrule.yaml`, driven by a `monitoring:` block in
its `values.yaml`. All of it is generated by `app/_generate.sh`, so the 59 services are consistent:

```yaml
# app/payment-gateway/values.yaml  (excerpt — generated)
monitoring:
  enabled: true              # alerting is MANDATORY; see "Mandatory by default" below
  app: bankobs               # umbrella label stamped on every alert (grouping / filtering)
  namespace: monitoring      # CRs go where Prometheus/Alertmanager run (the obs cluster)
  cluster: obs-v1-bankobs    # k8s_cluster_name on this service's infra metrics
  serviceNamespace: bankobs  # service_namespace (spanmetrics) + k8s_namespace_name (infra)
  team: payments             # label on RED alerts (grouping / filtering only)
  infraTeam: platform        # label on pod / deployment-health alerts
  errorRateThreshold: 0.05   # HighErrorRate fires above this 5m error ratio
  latencyP95Ms: 1500         # HighLatencyP95 fires above this p95, in ms
  # WHO is paged for THIS service → its own AlertmanagerConfig (SES transport stays global):
  emails: ["payments-eng@example.com"]        # every alert for this service e-mails here
  criticalEmails: ["payments-oncall@example.com"]  # severity=critical goes here instead; [] → use emails
```

Each service renders five rules, all scoped to its own `service_name` / deployment:

| Alert | Signal (OTel-native metric) | Team | Severity |
|---|---|---|---|
| `<svc>HighErrorRate` | spanmetrics `calls_total` error ratio > `errorRateThreshold` | `team` | critical |
| `<svc>HighLatencyP95` | spanmetrics `duration_milliseconds_bucket` p95 > `latencyP95Ms` | `team` | warning |
| `<svc>DeploymentDegraded` | `k8s_deployment_desired - _available > 0` | `infraTeam` | warning |
| `<svc>PodNotRunning` | `k8s_pod_phase` Pending/Failed/Unknown | `infraTeam` | critical |
| `<svc>ContainerRestarting` | `increase(k8s_container_restarts[15m]) > 3` | `infraTeam` | warning |

- Each rule is auto-labelled `app`, `team`, `severity`, `service`. `team`/`infraTeam` are there for
  grouping and filtering; **routing keys off `service` and `severity`** (see "Per-service routing" below).
- Prometheus templating (`{{ $value }}`) in annotations is emitted literally into the rendered rule.
- **Tune a service** by editing its `monitoring:` block (thresholds, recipients) — or `app/_generate.sh`
  to change all 59 at once, then re-run it. For an extra service-specific rule, add it to that chart.

### Mandatory by default — why the bankobs app release opts out

Alerting is **mandatory**: `monitoring.enabled` defaults to **true**, so every service renders its
`PrometheusRule` *and* `AlertmanagerConfig` — you can't ship a service with no alerting by forgetting a
flag. There is exactly **one** opt-out: the **app release to the bankobs cluster** (`app/Makefile`'s
`services` target and each service's `make deploy`) passes `--set monitoring.enabled=false`, because that
cluster has no Prometheus Operator and no `monitoring.coreos.com` CRDs — applying a CR there would fail.
Those CRDs and the operator live on the **obs cluster**, so `make app-monitoring` (Step 14) applies every
service's rule **and routing** there, next to Prometheus.

## Per-service routing (who is paged)

Each `app/<svc>` chart also renders its own `AlertmanagerConfig <svc>-routing` from the same
`monitoring:` block — so the chart that says *what* to alert on also says *who* to e-mail:

```yaml
# app/<svc>/values.yaml  (excerpt — the routing fields of the monitoring: block)
monitoring:
  emails: ["payments-eng@example.com"]             # every alert for this service e-mails here
  criticalEmails: ["payments-oncall@example.com"]  # severity=critical goes here instead (pager)
```

The rendered `AlertmanagerConfig` matches only this service's alerts (`service=<svc>`) and sends them to
`emails`; when `criticalEmails` is set, `severity=critical` peels off to that pager list instead (an
empty `criticalEmails` means critical just goes to `emails`). It carries the label
`alertmanagerConfig: app-monitoring`, so the operator **merges every service's config** into Alertmanager
with no central route table. The SES transport (smarthost/auth/From) is inherited from the global config.

Generated defaults: payments-domain services e-mail `payments-eng@example.com` with
`payments-oncall@example.com` as the critical pager; every other service e-mails `platform-sre@example.com`
(no separate critical list). Change them per service in its `values.yaml`, or fleet-wide in
`app/_generate.sh`.

**Add another app:** give its charts a `monitoring:` block with `app: foo` and its own `emails` — its
routing comes along automatically, no central chart to touch.

## Amazon SES setup (how e-mail is sent)

### 1. Get SES SMTP credentials and verify a sender
In the SES console (region `us-east-1`):
- **SMTP settings → Create SMTP credentials** → you receive an **SMTP username** and **SMTP password**
  (the SMTP password is *not* your AWS secret key).
- **Verified identities →** verify the **From** domain or address (e.g. `observability-alerts@lab.example.com`).
  If your SES account is still in the **sandbox**, also verify each **recipient** address, or request
  production access.

### 2. Point the config at your region / sender
In `values/kube-prometheus-stack.yaml` the global block is pre-set to
`email-smtp.us-east-1.amazonaws.com:587` with STARTTLS. Change the region host and `smtp_from` if
needed (or pass `SES_FROM=` at deploy).

### 3. Store the credentials (never in git)
```bash
make alertmanager-secret SES_SMTP_PASSWORD='<ses-smtp-password>'     # → Secret alertmanager-ses-smtp
```
The password is mounted into Alertmanager and referenced as `smtp_auth_password_file`. The **username**
and **From** are injected at deploy via `--set-string`:
```bash
make kube-prometheus-stack SES_SMTP_USERNAME='AKIA…SES' SES_FROM='observability-alerts@lab.example.com'
```
(For GitOps, `alertmanager/ses-smtp-secret.example.yaml` is the manifest form — feed it through
sealed-secrets/SOPS, don't commit a real password.)

## Deploy

On top of an existing stack (metrics/traces/logs already running — the cluster stays as-is):

```bash
# 1. store SES creds + apply the Alertmanager transport
make alertmanager-secret SES_SMTP_PASSWORD='<pw>'
make kube-prometheus-stack SES_SMTP_USERNAME='<user>' SES_FROM='alerts@you.com'

# 2. apply alerting: every service's own PrometheusRule + AlertmanagerConfig
make app-monitoring
```

`make app-monitoring` loops `../app/*/`, renders each service's `templates/prometheusrule.yaml` **and
`templates/alertmanagerconfig.yaml`** with `monitoring.enabled=true`, and applies the 59 `<svc>-alerts`
rules + 59 `<svc>-routing` configs to the obs cluster. `make all …` runs the whole stack in order and
includes this step. (There is no central routing release to install any more.)

## Verify end-to-end

```bash
CTX=obs-v1-observability

# Per-service CRs applied (one <svc>-alerts PrometheusRule + one <svc>-routing AlertmanagerConfig each):
kubectl --context $CTX -n monitoring get prometheusrule     -l app.kubernetes.io/managed-by=app-monitoring
kubectl --context $CTX -n monitoring get alertmanagerconfig -l app.kubernetes.io/managed-by=app-monitoring

# Rules loaded by Prometheus (per-service alert names):
kubectl --context $CTX -n monitoring exec deploy/kps-grafana -c grafana -- \
  curl -s 'http://kps-prometheus:9090/api/v1/rules' | grep -o '"name":"[a-z-]*High[A-Za-z]*"' | sort -u | head

# Per-service receivers merged into the live Alertmanager config (one <svc>-email, plus
# <svc>-critical for the payments services):
kubectl --context $CTX -n monitoring exec alertmanager-kps-alertmanager-0 -c alertmanager -- \
  amtool config show --alertmanager.url=http://localhost:9093 | grep -E 'name: .*-(email|critical)' | head
```

**Fire a real test** — an end-to-end SES probe, independent of any service's routing:

```bash
make pipeline-test        # arms bankobsAlertPipelineTest → routed to testEmail → SES e-mail
# watch it leave:
kubectl --context $CTX -n monitoring logs alertmanager-kps-alertmanager-0 -c alertmanager | grep -i 'smtp\|email\|notify'
make pipeline-test-off    # disarm when done
```

(`testEmail` is set in `app-monitoring/values-bankobs.yaml`. This probe routes only itself; it does not
touch any service's own `<svc>-routing`.)

If the logs show an SMTP **auth** error, the pipeline is correct but the SES username/password/From
aren't right yet — recheck step 2/3 above and that the From identity is verified (and recipients, if
in the SES sandbox).

## Files

| File | Role |
|---|---|
| `values/kube-prometheus-stack.yaml` | Alertmanager base config — **SES transport** + config-CR selectors |
| `../app/<svc>/templates/prometheusrule.yaml` | each service's **own rules** (RED + pod/deploy health), from its `values.yaml` `monitoring:` block |
| `../app/<svc>/templates/alertmanagerconfig.yaml` | each service's **own routing** (`emails` / `criticalEmails`), from the same block |
| `../app/_generate.sh` | generates all 59 charts incl. the per-service rule + routing templates and `monitoring:` defaults |
| `app-monitoring/` (chart) | optional **SES pipeline smoke-test** only (probe rule + its own route); no real routing |
| `app-monitoring/values-bankobs.yaml` | the probe's `testEmail` + `enableTestAlert` toggle |
| `alertmanager/ses-smtp-secret.example.yaml` | manifest form of the SES password secret (GitOps) |
| `Makefile` | `alertmanager-secret`, `app-monitoring` (per-service rule + routing loop), `pipeline-test`/`pipeline-test-off`, wired into `all`/`destroy` |
